# ADR-0002: 定義データの形式

- 状態: 承認（REV-002）
- 日付: 2026-10-14
- 関連要求: FR-MOD-01, FR-MOD-02, FR-MOD-04, IF-03, NFR-08, NFR-09

## 背景

アイテム・レシピ・施設などは定義データで記述し、本体のデータも MOD と同じ形式で読み込む（FR-MOD-02）。MOD 作者はテキストエディタで読み書きする（IF-03）。読み込みで任意のコードが実行されてはならない（NFR-09）。

## 決定

定義データは **TOML** で書く。Go のライブラリは [BurntSushi/toml](https://github.com/BurntSushi/toml) を使う。

```toml
[[item]]
id = "herb"
name = "薬草"
attributes = ["草", "癒し"]
```

## 理由

- **人が書きやすい**: コメントが書け、括弧の対応に悩まない。設定ファイルとして広く使われている
- **曖昧さが少ない**: YAML のように、`no` が真偽値になるといった暗黙の型変換がない
- **安全**: データしか表現できず、任意のコードの実行につながらない
- **誤りの位置を報告できる**: ライブラリが行番号付きでエラーを返す（FR-MOD-04）。未知のキーも検出できる

## 検討した代替案

| 案 | 採用しなかった理由 |
|---|---|
| JSON | 標準ライブラリだけで読めるが、コメントが書けず、末尾のカンマで誤りやすい |
| YAML | 書きやすいが、インデントや暗黙の型変換による誤りが起きやすい |
| Lua などのスクリプト | 表現力は高いが、データ MOD の段階では不要。安全性の確保が重い（スクリプト MOD は将来の別 ADR で扱う） |

## 影響

- 外部ライブラリへの依存が 1 つ増える
- 文法の検査は TOML ライブラリが行い、ゲームとしての意味の検査（参照先の ID が存在するか、属性が 3 個以下かなど）は自前のバリデータで行う
