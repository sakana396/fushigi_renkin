## 5. 進め方の振り返り

### うまくいったこと

- 設計の承認前に spec-reviewer が設計書をレビューし、tick の計算例や、core と ui のどちらで直すかといった曖昧な点を、実装の前に 14 件つぶせた（REV-017）
- テスト仕様書で Issue ごとにテストケースの連番の範囲を先に割り当てた（#28）。並行して作業しても、反復 1 のような ID の重複は起きなかった
- レビューでテストが弱い点を、ミューテーション（わざと誤った実装にしてテストが落ちるか）で見つけ、直したあとも同じ方法で確かめた（REV-019、REV-021）
- ui の手動テストで、検証用のデータのコピー（属性なし、2 枠のレシピ、一覧を増やしたデータ）を使い、本体のデータを変えずに境界と異常系を確かめられた（REV-022、REV-023）

### うまくいかなかったこと

| 問題 | 対策 |
|---|---|
| バックグラウンドで動かした Codex が標準入力を待ち、約 4 時間止まった | `codex exec` に `< /dev/null` と `timeout` を付ける（Claude Code のメモリに記録） |
| 並行した Issue が、トレーサビリティマトリクスの隣どうしの行を同時に変え、毎回マージで衝突した | 後からマージする側が両方の内容を残して解消した。行の衝突そのものは防げていない（今後の検討） |
| Codex の手動テストケースが正常系に寄り、設計の決まりの一部（ほかの枠の差し引き、割り当て直し、逆の向き）を確かめていなかった | spec-reviewer が指摘し、Claude Code がケースを足して確認した（REV-022、REV-023） |
| Claude Code の自己承認とみなされるマージは、自動マージの条件を満たしていても止められることがある（PR #26） | 人の明示の承認を得てからマージする |
