## 検証

- `gofmt -l .` は出力なし。`GOOS=windows go vet ./...` は成功（Linux では ui と cmd が X11 の不足でビルドできない）
- `go test ./internal/defs/... ./internal/defload/... ./internal/core/... ./data/...` は成功。`[[map]]` がない既存の目録と本体データも読める（DES-VAL-17）
- `go test -run=^$ -fuzz=FuzzLoadMaps -fuzztime=30s ./internal/defload/` は PASS（約 7.6 万回。40 秒・4 並列でも約 25.8 万回で PASS）。種は `f.Add` の 9 件で、通常の `go test` では種だけが走る
- `go run ./tools/tccheck` は整合 OK（警告はすべて既存の手動テスト）
- 誤り文は、設計書 3 章の例（DES-VAL-18〜23）と同じ形で出ることを確かめた。defs の型は 1.1 節のクラス図と合っている
- 修正前の変異の結果: 28 通りのうち 13 通りを検出し、15 通りが通り抜けた（うち 1 通りは他の規則が先に誤りになるので穴ではない）。town の必須設備、必須の出入り口、mark の重複と長さ、検証の進め方の止め方、出入り口のマスを通る塗りつぶし、Name と Look の写し忘れ、報告先のファイル名が当たる（指摘 1〜5）
- 修正後、Codex が必須設備・検証の順の 2 条件・出入り口を通らない塗りつぶしの 4 つの変異の検出を確かめた。Claude Code も、mark の形、mark の重複、到着のマスが床でない、town 行き・workshop 行き・gather 行きがない、の 6 つの検査をそれぞれ外し、どれもテストが失敗することを確かめた

## 指摘と対応

| # | 指摘 | 区分 | 対応 |
|---|---|---|---|
| 1 | DES-VAL-21・22 の一部（town の必須設備、必須の出入り口、mark の重複と長さ、到着のマスが設備や出入り口）に誤りの例のテストがない（中） | 設計どおりへの修正 | 誤りの例を足した（TC-FR-FLD-04-31〜39） |
| 2 | 検証の進め方の止め方（DES-VAL-21・22 の誤りで塗りつぶしをしない、DES-VAL-18・19 の誤りで DES-VAL-20〜22 をしない）のテストがない（中） | 設計どおりへの修正 | テストを足した |
| 3 | 塗りつぶしが出入り口のマスに入らないことのテストがない（低〜中） | 設計どおりへの修正 | 内側に出入り口を置いた地図のテストを足した |
| 4 | ファイル名と位置・理由を別々に確かめていて、同じ診断に両方があることを保証しない（低） | 設計どおりへの修正 | 診断ごとに File と `Path: Reason` を確かめる形にした |
| 5 | TC-FR-FLD-04-02 が、読み込んだ地図の Name・Start・出入り口の全項目を確かめていない（低） | 設計どおりへの修正 | 全項目を期待値と比べる形にした |
| 6 | 地図の外の `start` の理由が `"\x00"` になる（低） | 設計どおりへの修正 | 「開始位置 (x, y) が地図の外」と報告するようにし、テストを足した |
| 7 | FuzzLoadMaps の不変条件に DES-VAL-21・22 の一部がない（低） | 設計どおりへの修正 | 必須設備と出入り口の性質を独立に確かめるコードを足した（TC-NFR-08-02〜09） |
| 8 | `start` の x・y の片方の書き忘れが 0 として通る（低） | 設計どおりへの修正 | 片方の書き忘れも「開始位置が書かれていない」系の誤りにした |
| 9 | 誤りの並び順が map の順に依存する（低） | 設計の範囲内の改善 | 地図 ID・出入り口の数字の順に並べた |

## 実装者の判断事項

| # | 判断 | 判定 |
|---|---|---|
| 1 | 「地図がない」の報告先を最初の `[[map]]` のファイルにする | 設計の範囲内 |
| 2 | ID の誤り（DES-VAL-17）がある地図でも DES-VAL-20〜23 を行わない | 設計の範囲内（誤りを重ねて出さない考え方に合う） |
| 3 | 同じ行で、行の長さと知らない文字の誤りを両方報告する | 設計の範囲内 |
